# canon 终端试聊

`moirai canon test`（即 `run_canon_chat.py`）是独立的本机试聊入口，用来在真实 Bot 接入之前观察“检索到的片段 → 阿米娅回复”。它不经过 AstrBot、Core Event Protocol、Moirai 原有聊天记忆或正式的 B6–B9 注入路径，因此不能代替 [canon.md](canon.md) 里的 Bot 验收。本文件描述终端**当前**的行为，是证据预算和每轮流程的唯一出处；各轮改动的动机和测量结果见 [canon 对话质量](canon-dialogue-quality.md)（英文，按日期记录）和 [canon 检索实验](canon-retrieval-experiment.md)。代码结构和迁移到正式路径的指引见 [canon 运行时结构](canon-runtime-architecture.md)。

## 启动与选项

在终端直接运行（沿用已有的 `~/.local/bin/moirai` 命令）：

```bash
moirai canon test
```

- **数据库**：优先读 `.dev_data/canon/v10/all/build/canon.sqlite`（618 个场景、4,377 个事件）及其对应的向量索引；不存在时依次退回 100 场景和 20 场景的试聊副本，最后是旧的 Nexus 基准库。启动时打印选中的路径。`--db` 指定别的副本。全量库没有导入干员档案，也没有已审阅的时间事实。
- **人格**：默认 `devtools/canon/amiya_persona_concise.txt`；原来的完整人格用 `--persona-file devtools/canon/amiya_persona.txt`。
- **对话者**：默认是博士；`--not-doctor` 做身份对照。`--as-of <point_id>` 指定一个已审阅的剧情时间点。
- **模型**：模型类型依次取 `--model-type`、`CANON_CHAT_MODEL_TYPE`、`CANON_MODEL_TYPE` 和 `run_config.py` 的 `MODEL_TYPE`。API key 取自 `CANON_CHAT_API_KEY` 或所选模型的配置，从不打印。
- **观察**：`--show-sources` 或对话中输入 `/sources` 显示证据和路由决定；`--dry-run` 和 `--questions` 不调用对话模型。终端每轮显示证据估算、耗时，以及接口返回的 token 用量。

## 每轮流程

每轮按“理解 → 取证 → 组装 → 生成 → 检查 → 提交”六步处理，只有生成和检查会调用模型：

1. **理解**（本地）：按命名实体和问题意图选路线。会话在最多两轮无关闲聊之内保留已提到的话题，所以带类型的追问（人称代词、地点或组织的指代）能扩展检索词。简短的“为什么”追问可以带上之前提到的关系另一方。有歧义的指代不会产生新事实。长度至少四个字的名字里唯一的一处单字替换可以在查询中纠正，但不改写库里的实体。印象题用个人视角的综述证据；宽泛的动机排序要求点名双方，而且不代替针对具体人物事件的检索。
2. **取证**（本地）：闲聊不预取。剧情和近况轮次取有上限、带出处的事件。角色不知情（`unstated`）的事件仍可作为导航候选，但在填充有限的事实证据名额之前就被排除。问题同时问“发生了什么”和“博士与某人什么关系”时，会给关系单独保留一路查询，并补充附近已知的上下文。涉及双方关系的动机题，优先取 witnessed 或 experienced 事件里明确的目的陈述。宽泛综述只选角色知情的事件，相关度权重高于场景多样性。事件摘要里的身份括注，只有在原文对话同时出现两个名字时，才作为身份线索交给核验，不写回实体表。明确引用一句原话或称呼的问题会直接查原文台词，优先至多三个角色知情的匹配事件；没找到某句原话，不推断它从未说过。
3. **组装**：精简人格、对话者身份、有上限的证据和内存历史组成请求。对话历史按一份 5,000 估算 token 的预算挑选完整的问答对：放得下时保留开场一轮（不超过预算的四分之一）、最近的几轮，以及和本轮问题相关的较早轮次，最多十对。完整会话仍留在进程内存里；这只是发给接口的上下文上限。
4. **生成**：默认把 `canon_recall`、`canon_overview` 和 `operator_archive`（见下文“档案查询”）作为原生 tool 提供给模型（曾用 KCL arc:nexus 实测返回结构化 `tool_calls`，寒暄时不调用），模型觉得需要回忆时自行检索。每轮最多两次工具往返，工具往返不写入历史。`--no-tools` 可关闭；接口拒绝 `tools` 时本次会话自动改为不带工具。模型先回答再追问；具体的过去说法仍需要证据。
5. **检查**：删掉出戏和游戏机制的句子；终端允许自然的追问。具体剧情说法对照证据包核验；没有依据的引语和未经审阅的“现在”状态仍判不成立。对话里的引用（`C1` 等）只能说明谁在本次聊天里说过什么，不能证明世界事实。回复提到证据包里没有的名字时，先按这些名字补取一次证据再核验。修订可以修补被标出的句子一次，被判无依据的原句和证据包以外的名字不能回到修订后的回复里；修订中新写出的剧情说法再做一次最终核验，不通过就删掉那句。格式错误的核验结果每轮可重试一次；重新核验仍无效时按不通过处理。全程使用同一份本地证据包和明确的证据编号（事件 `E`、档案 `A`、已审阅事实 `F`）。
6. **提交**：只把整理和修订后的最终回复写进内存历史。

一轮的模型调用是：一次初始生成，加至多两次工具往返、一次核验、一次修订，以及必要时对新写事实句的一次最终核验。

## 证据预算

- 本轮证据累计上限的基础值是 `--token-budget`，默认 900 估算 token。之后的工具调用和档案查询共用这一轮的有效上限，不另开预算。
- 明确要求讲一段长剧情的综述，可以浮动到 2,400：先放按篇章和场景原文顺序排列、带出处的短提纲，再用剩余预算放原文行。
- 其他拥挤的综述，以及 hybrid 模式下的事实证据包，最多浮动到 1,200。事实证据包放宽时，事件摘要截到 220 字，优先保留原文行。离线全文模式的事实证据保持 900，不放宽。
- 只有基础值在 900–1,199 之间时才会浮动（长剧情综述要求基础值在 900–2,399 之间）；把 `--token-budget` 设成其他值时按原值执行。
- 以上都只属于终端。插件配置里的 `canon_token_budget`（默认 600）是给尚未实现的 B7 注入路径准备的，两者的关系还没确定，见 [canon 运行时结构](canon-runtime-architecture.md)。

## 检索

终端用 SQLite `mode=ro` 和 `query_only=ON` 读取数据库（可看到已提交的 WAL 内容），不调用会建表或更新 meta 的 `CanonStore.open()`。对话历史只保存在内存，单轮试聊不创建聊天记录、基准报告或日志，`--questions` 则创建本地检索评测报告。终端滚屏与远程模型服务方的请求留存由各自环境决定。发送给生成模型的内容包括当前问题、有限的内存历史、人格提示词和本轮命中的 canon 片段。

检索默认 `--retrieval auto`：这份库在所属构建目录里有派生向量索引（`<构建目录>/canon.retrieval/index-<哈希>.sqlite`，由 `moirai canon retrieval build --allow-remote --db <库>` 生成）时用 hybrid，没有时用离线的 baseline。hybrid 用加权 RRF（k=10）融合四路：向量 1.0、事件文本（主题、摘要、参与者、beats）的两字 BM25 0.3、原文台词的两字 BM25 0.8、实体 0.1；baseline 融合后三路，再做本地加权。两份 BM25 都是启动时在内存里建的，库内的 trigram 全文表（`events_fts`、`beats_fts`）和由 `import --embed` 写入的 `event_vec` 表都不参与终端检索。`--dry-run` 不加 `--allow-remote` 时始终离线。

被判为闲聊、但和某个事件足够相似、又在语料里有足够区分性词汇的问题，会改走剧情路线，显示为“剧情（检索判定）”；单看相似度会把问候、天气这类闲聊误判进剧情线，这是第二个条件存在的原因。设计、评测题库和结果见 [canon 检索实验](canon-retrieval-experiment.md)。

有上限的结构扩展会沿事件关系边和原文场景的前后衔接最多走两跳，最多返回六个上下文事件、每个场景至多三个，不额外调用向量或模型。它用在四个地方：情境综述从最强的命中事件出发；明确综述从前四个命中出发（印象题不扩展）；“为什么”类问题从前两个命中出发补两个事件；点名关系的问题为关系那一路补一个事件。抽取出的因果边和场景相邻只是导航线索，不证明世界时间、因果或角色知情。上限的具体数字见 [canon 对话质量](canon-dialogue-quality.md) 的 Retrieval and knowledge boundaries 一节。

## 综述路线

综述路线由 `core/canon/overview.py` 负责意图判断和跨场景选择。它从同一库的场景锚点、篇章名、官方简介、episode 与事件文本定位候选范围；篇章资料只用于导航，送进证据包的事实仍来自事件摘要和原文行。一次综述检索最多发一次向量查询，其余篇章聚合与多样性选择在本地完成；明确的长剧情综述最多选十六个事件，先按篇章与场景原文顺序加入带出处的短提纲，再按相关度填入每事件至多四条原文行；印象和情境综述仍最多选十个事件、两条原文行。终端会预取明确的综述和印象问题，模型也能用 `canon_overview(query)` 追补；该工具返回结构化的范围、代表性覆盖说明，以及带事件 ID、原文行键和知情渠道的证据。工具结果也受同一 token 估算上限约束，和预取共用本轮预算，不另开证据预算（见“证据预算”）。评测报告的 `overview_trace` 保留范围、候选、最终事件和原文行键。它是 Moirai 内部的模型工具接口，目前没有独立 MCP 服务或 Bot 运行时接入。

## 档案查询（operator_archive）

干员档案、NPC 情报和敌人图鉴在世界观里是罗德岛的人事档案和作战情报，是剧中存在的记录，所以作为阿米娅可以查阅的资料接入；星级、职业、技能、数值、卡池这类只有玩家才有的信息不导入，也仍按出戏处理。数据来自 Arknights-Texts v7 的 `exports/archive_pack/`（干员 434、NPC 5、敌人 948，敌人只收 BOSS 和精英），按 archive_hash 增量导入，不调用模型：

```bash
python -m core.canon.cli archive-import --pack ../Arknights-Texts/exports/archive_pack \
    --story-pack ../Arknights-Texts/exports/story_pack --db <canon.sqlite>
```

`--story-pack` 同时按新的实体种子刷新实体：补新实体和别名、更正种子实体的类型（如只以说话人身份出现的“整合运动”改为组织）、重写种子实体的 `entity_archives` 档案链接；抽取出的同名实体不动。schema_version 4 新增 `archives`、`archive_sections`、`entity_archives`，旧库打开时原地升级。

`operator_archive(name, section)` 由模型自行调用：先按别名找到实体再取它挂的档案，找不到时按档案名或英文代号匹配，干员档案排在敌人图鉴前面，每次最多两份档案、每份最多两段、每段最多 600 字。不指定段落时返回基础档案和客观履历（NPC 为情报资料一，敌人为作战情报），并列出这份档案还能查的段落。默认只返回档案本体形态的段落：升变档案（`PATCH` 解锁）、属于其他形态的段落（`patchIdList` 里没有这份档案本身）和标题为“？？？”的隐藏段都不返回，`--archive-all` 才全部返回；档案是游戏里的最新版本，可能超过阿米娅“当下”应知道的范围，这是保守默认的原因。查到的段落以 A 编号放进同一个证据包，渠道写“罗德岛档案记载，不是你亲历的事”，回复要求让她说成“档案上写着”；核验时 A 编号可以作为剧情和人设类说法的依据，说成亲历算不成立。

## 批量检索评测

现有自动检索题库可直接通过同一个 `test` 入口批量运行，不调用生成模型。省略 `--questions` 后面的路径时使用本机 `.dev_data/canon/eval/retrieval-200-v1.jsonl`（原 99 题、81 道新增事实题、20 道跨事件大问题）；每题独立检索，不沿用上一题的聊天历史。大问题各标三个原文支持的剧情要点，报告单列要点召回与至少覆盖两个要点的比例。全量库可这样测：

```bash
moirai canon test --questions
```

批量评测默认用离线 baseline；`--retrieval hybrid --allow-remote` 需要这份库对应的派生向量索引，并会向配置的 embedding 服务发送查询。先用 `moirai canon retrieval plan --db <canon.sqlite>` 估算，再显式运行 `moirai canon retrieval build --allow-remote --db <canon.sqlite>` 建索引。`--out <报告.json>` 可指定报告位置；未指定时报告写入这份库旁的 `canon.retrieval/runs/`。报告逐题记录路线、命中、最终和注入排名，并汇总最终召回、注入召回、答案行注入率与闲聊路线正确率。旧版 100 场景构筑可指定 `.dev_data/canon/eval/retrieval-200-v1-100-compatible.jsonl`，只测试它们实际包含答案的 128 题。大问题的三个要点是选定的代表性证据，其他相关事件可能同样有用；要点覆盖率是严格的锚点指标，不等同于最终回答质量。旧 100 题可显式指定 `retrieval-100-v2.jsonl` 复测。

请把试聊中发现的无关召回和回答问题记录下来，在 B6–B9 的正式 Bot 路径再验证。

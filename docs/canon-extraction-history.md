# canon 抽取版本记录

本文件按从新到旧记录抽取 prompt 每一版的动机、改动和试跑结果，只追加、不改写旧结论。当前的抽取流程、校验规则和基准用法见 [canon 抽取与基准](canon-extraction.md)，整体状态见 [canon：原作剧情记忆](canon.md)。

约定：保留在 `core/canon/prompt.py` 的 `PROMPTS` 里的版本一字不改，要改就另起新版本名；v8、v9 只是试跑草稿，没有保留。比较两版 prompt 时至少各跑两次，或者和同条件重跑的结果比，并注明模型——跨模型差异不能归因于 prompt。

## 知情渠道与事实来源分层（canon-extract-v11，可选试验）

设置 `CANON_PROMPT_VERSION=canon-extract-v11` 做一次独立的新抽取；默认仍是 V10，V10 的缓存输出不变。V11 保留 `views.channel` 表示在场与亲历关系，另给每个视角加一个窄的 `access` 列表。标签有四种：`direct_report`（阿米娅收到汇报）、`command_report`（博士或凯尔希收到汇报）、`record_available`（罗德岛确有的记录）、`role_candidate`（从罗德岛正式行动推断出的、按职务可能收到的简报）。每条标签写明接收者，只陈述传达的或相关的内容，并引用本事件内的原文行。`role_candidate` 始终只是候选：它不会把未目睹的事件变成 witnessed，也不证明阿米娅确实收到了简报。V11 还允许纯旁白事件的参与者列表为空。schema v5 把获知标签存在 `view_access`；V10 的行没有这些标签。终端 gateway 目前不把这些候选当作角色知识注入。

V11 的真实接口运行仍分两个有序阶段：先抽事件，再从已抽出事件的原文行里提出时间事实建议。第二阶段用 `canon-facts-v3` 和它自己的缓存。它给每条候选标来源 `observed`（观察到）或 `reported`（他人转述），时间标 `event`（事件当下）、`earlier`（更早）或 `unclear`（不明）。更早和不明的候选留在未锚定时间线上。转述的说法不能直接批准为世界事实，需要独立的观察证据。没有候选会被自动批准，也不会用来断言“现在”的状态。

授权外发数据后，小规模本机运行用 `CANON_PROMPT_VERSION=canon-extract-v11 .venv/bin/python run_canon_dev.py run`，并显式给出 `--scene`、`--facts`、`--no-probes` 和 `-y`。`build` 会处理整个 story_pack，只有用户另行批准全库运行后才能启动。

## 静默在场与情节结果（canon-extract-v10，当前默认）

100 场景 v7 库的复查发现两类数据问题。

一是渠道：36 个 unstated 事件夹在她在场的事件之间，其中约 10 个其实她就在现场，只是没有说话，例如 NL-10 胜负揭晓、6-16 灰喉的箭停在空中、0-4 博士下令 E3 出击。v7 的 witnessed 要求"文本表明她在场"，模型据此只看本事件里有没有写到她。

二是摘要：有的问题答案是没点名的人，比如"那天是谁来救的我们"，而 0-9 事件的摘要和 beats 里都没写"救援"。

这一版只改这两处：

- witnessed：本场景前文已经交代她身在此地、之后没有写她离开、镜头也没切到她不在的地点时，同一地点发生的事标 witnessed。证据引用交代她在场的那一行，可以在事件范围之外，校验本来就允许。镜头切走后又回到她所在的地点，回来后的情节她仍然在场。镜头在她不在的地点、别人背着她私下交谈，或者无法判断时，仍然用 unstated。
- summary：最后一句写明这段情节的结果（谁赶来解围、谁被救下、谁暴露了身份……），只写本场景已经发生的事，不写"为后文做铺垫"这类对剧情结构的评论。

版本经过：
- v8 是 14 个问题场景上的草稿。摘要规则原本写的是"结果或在情节里的作用"，7/108 条摘要因此写成了"为后续剧情埋下伏笔"这类评论。
- v9 改了措辞，评论降到 0。
- v9 在 NL-10 仍然在镜头切回赛场后丢掉她的在场，v10 为此补了"切走又回来"那一句。
- 每次改提示词都递增版本号，所以 v8、v9 只留作试跑记录。

对照实验：用 v7 prompt 原样再跑一次 100 场景（`v7/100/api/20260924-232732-rerun-kcl-arc_nexus`），检索同样下降。hybrid 最终 / 注入 / 答案行 / MRR 为 0.929 / 0.881 / 0.845 / 0.724，闲聊判对 13/15；baseline 为 0.738 / 0.655 / 0.643。可见"v7 原始"那次运行本身偏高，而题库、融合权重和路线阈值又都锚定在那一次上。和同条件的 v7 重跑相比，v10 的注入召回（0.917 对 0.881）和答案行（0.869 对 0.845）更好，最终召回和 MRR 略低，在运行间波动范围内；渠道明显更好（witnessed 56 对 22）。结论：v10 没有让检索变差，比较 prompt 时要用多次运行，或者和同条件重跑的结果比。

渠道的目标达成，结构没有退步。和"v7 原始"单次运行相比，检索没有提升：
- 题库偏向 v7：新增题是看着 v7 的标题写的，"细节·摘要"题按 v7 摘要挑选，答案行也取自 v7 的 beats。只看与版本无关的两类，用户 22 题从 0.95 降到 0.91（差 1 题），"细节·台词"都是 0.88。
- 0-9 救援题在 v10 里成为"临光突入战场击溃敌人"，向量名次从 30 升到 3，但融合后排第 9。
- 融合权重和路线阈值 0.54 都是在 v7 上选的。v10 的索引里，"早上好"的相似度是 0.581，"你最近睡得好吗"是 0.546，都越过了阈值。单纯调阈值无法分开闲聊和被救回的剧情题（两个分数区间完全重叠），2026-09-25 起检索判定增加了语料区分性词汇的第二个条件：全量库上闲聊分流恢复 15/15，事实命中逐题不变。设计、跨构筑验证与剩余损失见 [canon 检索实验](canon-retrieval-experiment.md) 的 Small-talk routing gate 一节。

v7 的 system prompt 原样保留。`core/canon/prompt.py` 的 `PROMPTS` 里同时放着 v7 和 v10，默认用 v10；用环境变量切换旧版重跑：`CANON_PROMPT_VERSION=canon-extract-v7 moirai canon run 100`，结果按版本号落在 `v7/` 下。保留的版本一字不改，要改就另起新版本名。v8、v9 只是试跑草稿，没有保留。

导入代码同时修正：participants 里能对上已有别名的名字写入 `event_entities`，不从 participants 新建实体。

检索评测改用与版本无关的金标准 `.dev_data/canon/eval/retrieval-100-v2.jsonl`：从 v7 的正确事件里取 beats 引用的行，细节题取含关键词的那一句作为答案行。命中的判定是"覆盖答案行的事件被取到"，另外单独统计"答案行出现在注入证据里"。事件切分变了也能直接和 v7 比较。

## 参考 v3 的细节密度（canon-extract-v7，已试跑）

v3 的 08-16 场景切成 6 个事件、每个事件 2 条 beats，视角证据分别引用不同参与回合；v6 是 4 个事件，其中一个参与事件已达 80 行。06-13 场景里，v3 的三个主要亲历事件分别有 12、14、18 行视角证据，v6 只有 4、4、5 行。17 场景 v3 是 10 个事件，多数事件有 3–4 条 beats；v6 切成 15 个，多数只有 2 条 beats，且重试两次。这些是结果差异，不能单凭一次样本证明某句 prompt 的因果作用。

v7 只修改抽取 prompt：沿用 v3 对长场景通常不超过 12 个事件的建议，同时保留 v4 起的整场行归属规则；目标角色参与且跨多个关键回合的事件通常保留 3–5 条不重复的 beats，不因 beat 名额单独强拆情节；视角证据覆盖她参与方式在事件中的不同重要回合，而不只取第一句。选取她的发言行时再次核对“已确认显示名”，避免把名单外相似名字当作她。输出结构、校验和评分口径均保持不变。

原定试跑顺序是先检查 06-13、08-16、17 和 19 的引用、回忆渠道及边界，再跑完整 20 场景；同模型比较时应把 `run_config.py` 的 `KCL_MODEL` 设为 `arc:nano`，并显式指定 v3 重新评分基线 `20260923-142027-rescore`。验收关注 20/20 成功、场景行覆盖不低于 0.99、没有低于 90% 的场景，以及探针覆盖、渠道正确召回、仿 KBF 和目标角色台词精确引用。

实际完成的是 Nexus 真实接口运行 `20260924-000545-kcl-arc_nexus`：20/20 场景成功，18 个首次通过、共 22 次调用；探针渠道正确的加权召回 0.976、仿 KBF 0.978、目标角色台词精确引用 0.910。用户人工审阅反馈没有明显大问题。探针仍是未经人工审定的草稿，且 Nexus 与此前 v3 的 `arc:nano` 是不同模型，不能把跨模型差异归因于 prompt。下一步按当时计划的 20 场景 Bot 试跑验证检索和最终回答。

## 恢复结构和证据稳定性（canon-extract-v6，已试跑）

v6 在 `normalize_output()` 中只补无歧义的缺失事件 id：已有 id 必须与数组位置的 e1、e2……一致，且 views 必须恰好引用每个预期 id 一次。已有 id 错位、views 缺失或重复时仍交给原校验；事件证据的遗漏或重叠不自动修补，因为不能确定哪一个事件应拥有那些原文行。

prompt 保留 v4 的整场归属和往事拆分要求，去掉 v5 的“超过五个关键事实就拆事件”指令，事件只在自然断点切。beats 可以引用支撑同一事实所需的前后几行，不再要求只摘孤立的单行；视角证据保留能说明参与方式的重要发言和态度转折，避免长对话只引第一句。每个事件都要显式填写顺序 id，防止依赖本地修正。

v6 真实接口运行 `20260923-232531-kcl-arc_nano` 完成 20/20 场景，02 首次通过，17 第三次通过；25 次调用耗时 709.7 秒。场景行覆盖 0.998，探针加权覆盖 0.833、渠道正确召回 0.738、仿 KBF 0.776、目标角色台词精确引用 0.730。08-16 的精确引用从 v5 的 16/53 回升到 38/53，仍低于 v3 的 52/53；06-13 仍为 16/43，v3 是 43/43。17 的回忆探针仍未精确命中，19 的回忆仍被并进当下事件，且 17 有一处名单外的“小阿米娅”台词进入视角证据。v6 没达到 v3 的质量；本次报告沿用了 Luna v1 基线，这里的 v3 数字来自同模型运行的重新评分结果。

## 关键细节精确引用（canon-extract-v5，已试跑）

同一批 20 个场景的 KCL `arc:nano` 真实接口运行里，v4 把事件覆盖的场景行比例提高到 0.997，但金标准探针的加权覆盖率从 v3 重新评分后的 1.000 降到 0.845，渠道正确的加权召回从 0.833 降到 0.702。场景 `obt/main/level_main_08-16_beg` 的目标角色台词精确引用从 52/53 行降到 14/53 行，beats 从 12 条降到 8 条，事件从 6 个合并到 4 个。部分探针的锚点仍落在事件范围里，却没有被 beats 或视角证据引用。这是一次运行的观察，不能单凭它断定 prompt 是唯一原因；45 条探针也仍是未经人工审定的草稿。

v5 保留 v4 的整场归属规则、输出结构、校验和评分口径，调整抽取 prompt：有不同关键行动、决定或话题转折时按自然断点拆事件；从事件的开头、中间和结尾挑选值得单独检索的事实，优先目标角色的决定、行动、态度变化和重要台词；每条 beat 只引用支撑它的具体行，不能用整段范围代替；目标角色参与且有可检索事实的事件至少写一条 beat。长事件若有超过五个独立要点，在自然断点拆开，不为满足建议的事件数而压缩要点。视角证据也引用能说明参与或获知方式的具体行。事件的 `evidence` 仍表示它占用的全部行；往事与当下事件不重叠。

v5 的 20 场景真实接口运行 `20260923-230051-kcl-arc_nano` 只有 18/20 成功。02 场景的前两次回复缺少 e2、e3 的事件 id，但 views 已按顺序引用它们；手动只补上这两个 id 后，第一次回复通过现有校验。17 场景的三次回复含大段证据重叠或遗漏，不能机械修补。完整运行的加权覆盖率 0.655、渠道正确召回 0.560、仿 KBF 0.610；场景行覆盖仍有 0.999，但台词精确引用降到 0.539。排除失败的 02 和 17 后，在共同成功的 18 个场景里，v5 加权覆盖率 0.821、渠道正确召回 0.701，略高于 v4 的 0.806、0.687；同范围的台词精确引用仍从 v4 的 0.750 降至 v5 的 0.539。v5 报告沿用了本机默认的 Luna v1 基线，以上 v4 数字按同一批场景重新对齐。v5 未达到验收标准。

## 事件铺满整场（canon-extract-v4）

v3 只说"她不在场的部分可以更粗"，没说这部分必须写，也没说事件证据是整段范围还是关键行。同一批 prompt 用 arc:nano（真实接口）、GPT-6 Luna 和 Claude Sonnet 5（都是每个场景一个全新上下文的 subagent）各跑 20 个试跑场景，三个模型在这些地方各行其是：

- **整段情节没进任何事件**：arc:nano 在场景 04 只覆盖 11% 的行；Luna 在场景 17 漏掉 L177–L265，这一段里有她的第二段回忆；Sonnet 在场景 10 只抽了一行转述，在场景 13 只抽了她出场的最后 25 行，前 196 行都没有。45 条探针只考和她有关的锚点，看不出这种遗漏：Sonnet 的仿 KBF 调和分反而最高（0.978）。
- **往事既单独成事件，又留在当下事件里**：Luna 在场景 17 拆出了 recalled 事件（L164–L169），但当下事件 L136–L176 仍然包含这几行，summary 也复述了这段回忆。
- **事件证据的写法不一致**：三个模型大多把事件证据写成整段范围（事件范围内平均 93%–98% 的行都列出），但每个模型都有只挑关键行的场景：arc:nano 的场景 04、15，Luna 的场景 20，Sonnet 的场景 12、17。同一个模型在不同场景里写法也会变。
- **事件数**：同一批场景分别是 106、102、165 个。两两对比时，渠道 κ 在 0.72–0.78 之间，事件 F1 只有 0.64–0.82。

v4 只改这几处，别的不动：

| 改动 | 内容 |
|---|---|
| 事件铺满整场 | 所有事件按顺序铺满整个场景，每一行属于且只属于一个事件；她不在场的部分也要写成事件，可以更粗，channel 用 unstated |
| 事件证据 = 占用的行 | `evidence` 写这个事件占用的全部行，用区间写（`["L8-L20"]`，不连续时写多个区间）；关键台词放进 beats 和视角证据。区间写法本来就由 `normalize_output` 展开，单个区间的跨度上限从 200 行放宽到 1000 行 |
| 往事从当下事件里去掉 | 单独拆出的往事占用的行，要从当下事件里去掉（当下事件的证据因此可以是前后两段），当下事件的 summary 也不复述这段往事 |
| "？？？"不猜 | 在任何字段里都不要猜"？？？"是谁，照写"？？？"。Sonnet 在场景 09 把"？？？"当成了珀茜瓦尔，并认为这条规则只约束目标角色 |

校验新增两条规则，不满足就带着行号整次重试，因为空出来的情节和重复占用的行都没法在本地补回来：

9. 本块里连续超过 5 行不属于任何事件，就算失败（`MAX_UNCOVERED_RUN`）。标题、过场这类零散的几行可以不归属。
10. 两个事件的证据共享超过 2 行，就算失败（`MAX_SHARED_LINES`）。

事件数仍然不设硬性上限。报告总览新增"事件覆盖的场景行比例"和"事件覆盖不到 90% 的场景"两项。把三次 v3 运行的输出直接过这两条规则，分别有 4、2、5 个场景会被拦下，拦下的正好是上面列出的这些问题。

已知局限：`audit.cited_lines` 对没有 beats 的事件，仍然把事件证据算作精确引用。v4 的事件证据是整段范围，所以这种事件会让"她的台词被引用的比例"偏高。v3 的三次运行里，每个事件平均有 2.6–3.7 条 beats。

## 事件粒度（canon-extract-v3）

v2 在 KCL `arc:lite` 上把一段交火拆成一拍一拍：场景 01 有 8 个事件，其中 5 个是她只在旁边看的碎片，每个只有一行视角证据。这样拆，检索时抓不到主线，注入名额会被同一段情节的碎片占满，输出 token 也会随事件数增加。只减少事件数，150 字的 summary 又装不下一整段情节。v3 按下面几篇论文验证过的做法改成两层：

| 做法 | 实现 | 依据 |
|---|---|---|
| 事件 = 一段连贯的情节，只在自然断点切 | prompt 列出断点：场景或地点转换、一段对话或一轮交锋结束、话题转折，再加上她的参与方式改变；每个事件通常 8–40 行，每个场景通常 2–8 个事件 | SeCom：话题连贯的段落级记忆单元优于按轮次（过碎）和按会话（过粗）；ReadAgent：叙事长文在自然停顿点分页，并限定每页的最小和最大长度；Michelmann et al.：LLM 切分叙事事件与人的共识一致 |
| summary 用"缩写"写法，放宽到 300 字 | 按顺序保留起因、关键动作、台词要点和结果，而不是一句概括 | ReadAgent：让模型"缩写"比"总结"更能保留叙事流程；SeCom、LongMemEval：只用摘要当记忆会丢细节 |
| 细节作为检索键，不单独注入 | 每个事件附 0–5 条 `beats`（每条最多 25 字，带证据行），存进 `event_beats` 并建立 `beats_fts`；M2 检索时命中 beat，注入的是它所属的整个事件，再加上这条 beat 对应的原文行 | LongMemEval：保留原内容、把抽出的事实作为额外的检索键，recall@k 提高 9.4%，QA 提高 5.4%；MemGAS：多粒度并存优于单一粒度；ES-Mem：记忆单元同时保存摘要和原文，去掉原文时效果下降最多 |

事件数不设硬性上限，免得触发整次重试。`audit.py` 把"事件超过 8 条""事件只覆盖不到 3 行（场景至少 20 行时）""beat 证据不在事件证据里"作为提示写进报告，报告总览里有 beats 的数量。

出处：

- Pan et al., *On Memory Construction and Retrieval for Personalized Conversational Agents*（SeCom，ICLR 2025），[arXiv 2502.05589](https://arxiv.org/abs/2502.05589)：LOCOMO 上段落级 71.57、按轮次 65.58、按会话 63.16、摘要记忆 53.87（GPT4Score）；零样本 LLM 切分在 DialSeg711 上 F1 0.888。
- Lee et al., *A Human-Inspired Reading Agent with Gist Memory of Very Long Contexts*（ReadAgent），[arXiv 2402.09727](https://arxiv.org/abs/2402.09727)：断点选在场景转换、对话结束、叙事转折处，每页 280–600 词（QuALITY/QMSum）；NarrativeQA 的 ROUGE-L 比最好的检索基线高 31.98%。
- Wu et al., *LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory*，[arXiv 2410.10813](https://arxiv.org/abs/2410.10813)：用摘要或事实替换原内容会损失 QA；以事实做扩展检索键，recall@k +9.4%、QA +5.4%。
- *ES-Mem: Event Segmentation-Based Memory for Long-Term Dialogue Agents*，[arXiv 2601.07582](https://arxiv.org/abs/2601.07582)：基于事件分割理论切分，记忆单元保存边界描述、摘要和原文；消融实验中去掉原文下降最多。
- *From Single to Multi-Granularity: Toward Long-Term Memory Association and Selection of Conversational Agents*（MemGAS），[arXiv 2505.19549](https://arxiv.org/abs/2505.19549)：会话、轮次、摘要、关键词多粒度并存，LongMemEval-s F1 20.38，单一粒度 13.78。
- Michelmann et al., *Large language models can segment narrative events similarly to humans*，[arXiv 2301.10297](https://arxiv.org/abs/2301.10297)：GPT-3 切出的叙事事件边界比单个人工标注者更接近人工共识。
- Fountas et al., *Human-inspired Episodic Memory for Infinite Context LLMs*（EM-LLM），[arXiv 2407.09450](https://arxiv.org/abs/2407.09450)：按事件切分并做边界修正，使单元内部连贯、单元之间分开；这里只借鉴了"单元内连贯、单元间分离"的原则，没有用它基于 surprise 的切分算法。

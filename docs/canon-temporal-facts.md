# canon 时间线事实与回复 Gateway

状态：全库候选构建与审阅包生成已实现（schema v3、可续跑分块抽取、偏序解析、终端 gateway）；候选须经审阅才进入事实查询。正式 Bot 的 B6–B9 注入仍未实现。Arknights-Texts 原规格 v1.4 尚未同步修订，以下内容是本地扩展；真实剧情文本、story_pack、试跑数据库和模型输出不提交到 Git。

## 为什么现有字段不够

`scenes.narrative_pos` 是 story_pack 的导出排序号，不是泰拉世界的时间；主线与活动、密录不能凭这个数字直接比较先后。`events.in_world_time` 的 `present` 仅表示事件发生在该场景的叙述当下，`past` 表示该场景在讲往事，两者都没有给出跨场景日期。`scenes.release_date` 是现实中的发布时间。现有 `edges` 只连接同一场景里的事件，不记录“后来发生的事改变了先前状态”。

因此，“甲曾在据点 A”有原文证据，不等于“甲现在仍在 A”。只凭最近一条命中或最大的 `narrative_pos` 选当前状态，会在稀疏的 20 场景试跑库里给出错误结论。现有 B6 的 `narrative_pos ≤ time_point_pos` 只是一种事件检索范围限制，不能复用作事实有效期或跨时间线的先后判断。

## 四个独立坐标

| 坐标 | 含义 | 来源与用途 |
|---|---|---|
| 叙述点 | 文本在什么场景、哪几行作出陈述 | `scene_key`、`event_id`、`line_key`；是可追溯的证据位置 |
| 发生点 | 所述事件在世界中何时发生 | 规范化时间点或有证据的先后关系；回忆不能直接用讲述场景的时间 |
| 有效区间 | 一条状态事实从何时成立、何时被改变 | 事实的开始、结束和变更证据；结束为空不自动表示仍然有效 |
| 获知点 | 角色何时、以什么渠道得知此事 | 第一阶段只复用 `views.channel` 与其证据；获知时间点尚未建模，与世界事实真伪分开判断 |

现实发布时间只用于数据版本和增量导入，不进入世界时间比较。每个时间点带所属时间线（主线、活动等）、精度、来源；两条时间线只有存在明确锚定关系时才可比较。不能比较时返回“不确定”，不能按导出顺序强排。

## 事实记录与证据链

一个事实只陈述一件可检验的事：`subject`、受控 `predicate`、`object`、肯定/否定、发生点、有效区间、持续规则和审核状态。第一批谓词限于会随剧情改变的状态，例如地点、拘押关系、组织归属、存活状态；人物印象和概括性情绪继续留在事件或认知层。持续规则至少区分“只在该点观察到”“有明确区间”“持续到有证据的变更”。模型不能仅因没找到后续事件，就把结束点填成“无限期”。

已新增的独立表：

- `timeline_points`：世界时间点、所属时间线、精度、场景与行来源；`timeline_before`：带证据的先后关系。只形成偏序，不强造全局日期。
- `facts`：原子事实、主体与客体、谓词、发生点、有效期、持续规则、来源类型和审核状态。
- `fact_evidence`：`fact_id → event_id → line_key`，标明支持、否定或变更；必须能回到原文行。
- `fact_transitions`：两条事实之间的 `supersedes`、`contradicts` 或 `corroborates` 关系，以及促成变更的事件和证据。互斥状态只有在时间可比且变更有证据时才关闭旧区间。
- `fact_coverage`：按时间线分别记录场景覆盖（`sparse` / `continuous`）与事实审阅覆盖（`none` / `partial` / `reviewed`）；缺失过渡场景时不能把“最后看到的状态”升格为“当前状态”。

事实来源设计包含原文明示、确定性推导和未核实模型建议；第一阶段的审阅导入只接受原文明示。模型建议不得直接变成已证实的事实；事实抽取使用 `canon-facts-v2` 和 `fact_extractions` 缓存，不使已有 v7 事件抽取缓存失效。相冲突的证据两边都保留，等待人工审阅，不覆盖旧记录。

## 查询时的判断

输入包含主体、谓词、`as_of`（可选世界时间点）、角色与查询用途。输出除了命中事实，还包含判定状态与完整证据链：

1. 查找同一主体/谓词的事实和变更，先确认时间点是否可比、证据是否充分。
2. 指定 `as_of` 时，按发生点与有效区间判断；后来发布的往事不因发布时间较新而覆盖当时状态。
3. 未指定 `as_of` 却问“现在”时，若没有明确的世界时间锚点和足够覆盖，返回 `unknown_current`；可以附 `last_known`，但必须标注来源时间，不用现在时复述。
4. 有明确变更证据且在查询点之前时，旧事实为 `superseded`；没有变更证据但覆盖不足时是 `last_known`，不是 `active`。时间不可比或证据相冲突时分别返回 `incomparable`、`conflicted`。
5. 角色获知渠道单独附上；`unstated` 表示文本未说明角色是否知情，不裁定世界事实为假，也不能说成角色亲历。

回答所依赖的链应可显示为“答案中的主张 → 当前/过时/不确定的事实版本 → 支持或变更事件 → 原文行 → 角色获知渠道”。若链缺少时间锚点或过渡证据，Bot 应说清楚最后可核实的是何时，避免自行补齐“每天探望”“现在仍在舰上”等细节。

## 自编验收例子

| 资料 | 查询 | 应得结论 |
|---|---|---|
| 场景 S1 明确甲在 A；S2 明确甲离开 A 并到 B，且 S1 早于 S2 | S1 时甲在哪？ | A，附 S1 证据 |
| 同上 | S2 后甲还在 A 吗？ | 否；A 已被 S2 变更，附两段证据 |
| 只有 S1 的稀疏样本 | 甲现在还在 A 吗？ | 当前未知；最多给“在 S1 时位于 A” |
| S3 晚发布，却在叙述早于 S1 的回忆 | S2 后甲在哪？ | S3 不覆盖 S2 的事实 |
| 两条不可比较的活动时间线都陈述甲的所在 | 甲现在在哪？ | 时间不可比，不能任取一条 |
| 同一时间点两条来源互相矛盾 | 甲当时在哪？ | 冲突，列出双方证据供审阅 |

## 全库构建与审阅路径

当前 story_pack 的 manifest 有 618 个场景。`moirai canon build` 使用 `.dev_data/canon/v10/all/build/canon.sqlite`，一次命令先按 V10 增量抽取全部事件，再按事件证据行抽取时间事实候选。重复执行同一命令会沿用成功场景的事件缓存，以及成功场景/成功分块的事实缓存；单场景事实接口失败不会停止其他场景。每块至多约 6500 字，连续失败最多重试四次；事件分块也按连续失败四次封顶。事件抽取失败的场景会明确记为跳过，命令返回非零状态；不会把没有事件证据的场景当作已完成事实抽取。可以用 `moirai canon estimate all` 先看事件阶段规模；真实接口的 `moirai canon run` 默认追加事实候选阶段，`--no-facts` 才跳过。`moirai canon run all` 做一次完整基准时也自动执行事实候选阶段，但基准每次新建数据库，实际全库续跑应选 `build`。这两个命令由本地 `run_canon_dev.py` 驱动，模型取自 `run_config.py`。

```bash
moirai canon estimate all
moirai canon build
moirai canon test --db .dev_data/canon/v10/all/build/canon.sqlite
```

`python -m core.canon.cli import --pack <story_pack> --db <canon.sqlite> --api-url <地址> --model <模型> --facts` 也是可续跑的底层入口，并在数据库旁写出 `review.html`；从环境变量 `CANON_API_KEY` 读取密钥。对已有库可用 `facts-suggest --db <库> --api-url <地址> --model <模型>` 单独续跑事实阶段。所有模型调用都只由用户显式执行这些命令触发。旧 Nexus 基准原件不能用于会迁移/写入的命令；使用数据库副本。

全量输出留在本机的忽略目录：`review.html` 按场景并排显示原文、事件和待审阅时间事实；`facts-candidates-*.jsonl` 是逐场景候选，`facts-candidates-*.report.json` 记录完成、失败、跳过和原因，`facts-candidates-*.review.json` 是可编辑审阅包。审阅包已为每条候选生成稳定 `fact_id`、时间点和证据引用，按主体/谓词列出重复或状态不同的 `review_groups`，无需人工从零拼装 JSON。默认全部是 `review_status=candidate`、`source_type=suggested`、`persistence=point`，`before`、`transitions`、`coverage` 为空。回忆和没有明确时间锚的事件放在独立的未锚定时间线；即便属于同一合集，也不会仅凭导出顺序自动建立世界时间先后。

审阅者核对原文后，仅把确有证据的候选改为 `review_status=reviewed`、`source_type=explicit`；若有明确的跨场景先后或状态变更证据，再填 `before` / `transitions` 并将其标记 `reviewed`。`facts-apply --db <库> --input <*.review.json>` 会筛出批准项并原子导入，其他候选仍留在本地审阅包，不会进入事实查询。`coverage` 只在核实世界时间范围与事实审阅完整性后手动填写并批准；全库场景数齐全不等于知道故事世界的“现在”。已导入的 fact 可用 `facts-query --subject <人物> --predicate location [--as-of <point_id>]` 核对证据链。重复导入相同 ID 会失败并回滚，增量批准时应从新审阅包选新 ID，或先在数据库副本验证。

在审核与时间关系建立前，即使 618 个场景的候选抽取全部成功，终端试聊对“现在怎样”仍只会说最后记得的情况和之后不清楚。这是正确的保守行为；模型建议与剧情时间顺序不能因为数量足够就自动升格为已证实事实。正式 Bot 的注入与最终回复网关仍需 B6–B9 路径，当前只对终端试聊有效。2026-09-25 的 V10 全库 Nexus 运行已生成 5,930 条候选，覆盖 616/618 个场景；另 2 个场景的事件抽取失败，事实阶段因此跳过。其中 `act16mini_st04` 是接口瞬时 429，重跑即可补上；`level_st_08-01` 开场是无角色的哲学旁白，模型在两次运行、八次以上调用中始终输出空 participants，无法通过校验，需要后续修订抽取 prompt（并列出 participants 为空时的事件类型规则）才能收录。审阅包内 5,930 条仍全部是 `candidate/suggested`，数据库 `facts=0`、`fact_coverage=0`。人工审阅和批准导入尚未执行。

本次审阅包有 764 个按主体/谓词汇总的组，其中 654 组包含不同客体；这可能是正常状态变更，也可能是抽取错误，不能仅凭客体不同判为矛盾。审阅时先核查查询影响最大的生死与拘押状态，再按常问人物处理地点和组织归属；每条都对照原文行，只有能证明跨场景先后或变更时才补 `before` / `transitions`。另有 165 个未锚定时间点，须保留时间不可比结论。只有核实相应时间线的场景连续性和事实审阅完整性后才能批准 `coverage`。

全量人工审阅不现实，第一批审阅按主体切窄。`python devtools/canon/fact_focus.py --db <库> [--subjects 主体1,主体2]` 从最新 `facts-candidates-*.review.json` 切出主体子包（仍是 canon-fact-review-v1 格式，`{DOCTOR}` 归一为“博士”），并在审阅包旁生成同名审阅页：按主体/谓词分组、按叙事位置排序，每条候选并列其原文行，多客体的冲突组标色。页面勾选“原文明确写明”的候选后可一键导出已审阅子集（自动置 `review_status=reviewed`、`source_type=explicit`），再用与全量相同的 `facts-apply` 导入。2026-09-25 的核心主体子包（阿米娅、博士、凯尔希）为 901 条候选、12 个多客体组。窄范围只让事实查询先在少数人物上可用，其余主体分批审阅；`coverage` 的批准门槛不因窄范围降低。

`moirai canon test --db <副本>` 读取同一个解析器。只有 `scene_scope=continuous`、`fact_scope=reviewed` 且有当前剧情锚点时，省略 `--as-of` 的状态才可能判为截至已导入剧情的有效事实；这仍然不等于现实中的“今天”。20 场景 Nexus 库没有这些条件，问塔露拉现况时，阿米娅只能说最后记得的情况，对她现况的断言会被 gateway 判为无依据。`--as-of` 接受已审阅的世界时间点 ID，不再把场景导出顺序当成世界时间。

每轮的检查流程见 [canon.md](canon.md) 的“临时终端试聊”：闲聊不核验；回复含剧情内容时由同一模型逐句核验，无依据的句子只修订一次，被判无依据的原句和证据包以外的实体不能回到回复里，只有最终回复写入内存历史。每轮最多一次生成（每次工具往返另加一次）、一次核验、一次修订。核验器本身也可能漏判；只有确定性部分（证据编号、时间偏序、覆盖、缺证据的当前状态、结尾问句与出戏词）可以硬性保证。正式 AstrBot/B6–B9 路径尚不存在；当前 Core Event Protocol v1 的 contribution 只有 prompt 文本块、reply_prefix 等，没有替换最终回复的操作。因此这个 gateway 目前只保护终端试聊，不能宣称已保护真实 Bot。
